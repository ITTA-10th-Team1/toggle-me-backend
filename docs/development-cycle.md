# Development Cycle

출처: 팀 Notion `BE` > Git Branch Naming Convention, Git Commit Message Convention

## 브랜치

| Prefix | 사용 기준 | 예시 |
| --- | --- | --- |
| `main` | 배포 가능한 상용 버전 | `main` |
| `develop` | 개발 통합 및 PR 기본 도착지 | `develop` |
| `feat/` | 새로운 기능 개발 | `feat/google-login` |
| `fix/` | 개발 중 발견된 버그 수정 | `fix/duplicate-subscriber` |
| `hotfix/` | 배포 후 긴급 수정 | `hotfix/token-error` |
| `refactor/` | 기능 변화 없는 코드 구조 개선 | `refactor/referral-count-calc` |
| `chore/` | 설정·문서·테스트 등 보조 작업 | `chore/querydsl-setting` |

> 팀 Notion 미작성: 브랜치 구조, 기본 형식, 이슈 번호 형식, 작성 기준, 예시, 선정 이유 (블록은 있으나 내용이 비어 있음)

## 커밋 메시지

### 기본 형식

```plain text
<type>(<scope>): <description>
```

### Type

| Type | 사용 기준 | 포함 이유 |
| --- | --- | --- |
| `feat` | 새로운 기능 추가 | 사용자 또는 시스템에 새로운 동작이 추가되는 변경의 명확한 구분 |
| `fix` | 버그 수정 | 잘못된 동작을 바로잡는 변경의 빠른 식별 |
| `refactor` | 기능 변화 없는 코드 구조 개선 | 기능 추가·버그 수정과 내부 품질 개선의 분리 |
| `test` | 테스트 코드 추가 및 수정 | 테스트 범위와 검증 로직 변경의 독립적 추적 |
| `docs` | 문서 추가 및 수정 | 실행 코드에 영향을 주지 않는 문서 변경의 구분 |
| `build` | 빌드 도구, 의존성, 프로젝트 설정 변경 | Gradle 및 라이브러리 변경처럼 빌드 결과에 영향을 주는 작업의 식별 |
| `ci` | CI/CD 설정 및 스크립트 변경 | 배포 파이프라인과 애플리케이션 코드 변경의 분리 |
| `perf` | 성능 개선 | 기능 변화 없이 처리 속도나 자원 사용량을 개선한 변경의 추적 |
| `chore` | 위 유형에 포함되지 않는 유지보수 작업 | 소스·빌드·문서 변경으로 분류하기 어려운 보조 작업의 수용 |
| `revert` | 이전 커밋 되돌림 | 기존 변경을 취소한 이력의 명확한 표현 |

분류 원칙
- 커밋의 **주된 목적**을 기준으로 Type 선정
- 하나의 커밋에 여러 목적이 섞인 경우 커밋 분리
- 판단이 어려운 경우 `chore`를 우선 사용하지 않고 변경 목적 재확인

별도 Type 미사용

| Type | 미사용 이유 | 대체 Type |
| --- | --- | --- |
| `design` | 백엔드 저장소에서 독립적인 디자인 변경의 발생 가능성 부족 | 변경 목적에 따라 `feat` 또는 `fix` |
| `comment` | 주석 또한 코드 또는 문서 변경의 일부 | `docs` 또는 `refactor` |
| `rename` | 파일·변수명 변경은 대부분 리팩터링의 일부 | `refactor` |
| `remove` | 삭제 자체보다 삭제 목적이 중요 | `feat`, `fix`, `refactor`, `chore` 중 선택 |
| `settings` | 설정 변경 범위가 모호하고 `build`, `ci`, `chore`와 중복 | 변경 대상에 따라 `build`, `ci`, `chore` |

### Scope

Scope는 변경이 발생한 핵심 도메인 또는 모듈을 표시한다.

| Scope | 적용 범위 |
| --- | --- |
| `auth` | 로그인, Access Token, Refresh Token |
| `member` | 회원 정보 및 프로필 |
| `room` | 공간 생성·조회·수정·삭제 |
| `item` | 물건 등록·조회·수정·삭제 |
| `global` | 공통 응답, 예외 처리, 보안 공통 설정 |
| `image` | S3 이미지 업로드 및 관리 |

- 영문 소문자, 단수형
- 클래스명이나 메서드명이 아닌 도메인 경계 사용
- 변경 대상이 명확한 경우에만 선택적으로 사용
- 중심 도메인이 없는 공통 변경은 Scope 생략
- 여러 도메인에 걸친 변경은 가장 핵심적인 도메인 선정

### Description

| 작성 기준 | 적용 규칙 |
| --- | --- |
| 언어 | 한글 사용 |
| 표현 | 명사형 종결 |
| 내용 | 무엇이 변경되었는지 중심으로 작성 |
| 길이 | 50자 이내 권장 |
| 마침표 | 문장 끝 마침표 미사용 |

```plain text
feat(room): 공간 생성 기능 추가
fix(item): 물건 조회 오류 수정
refactor(member): 회원 프로필 수정 로직 분리
build: QueryDSL 의존성 추가
```

| 지양 표현 | 사유 | 개선 표현 |
| --- | --- | --- |
| `feat(auth): 로그인` | 변경 내용의 구체성 부족 | `feat(auth): Access Token 재발급 기능 추가` |
| `fix(item): 오류를 수정했습니다.` | 서술형 종결 및 마침표 사용 | `fix(item): 물건 조회 오류 수정` |
| `refactor: 코드 정리` | 변경 범위와 결과의 불명확성 | `refactor(member): 회원 프로필 수정 로직 분리` |

### 커밋 단위

하나의 커밋은 **하나의 논리적 변경 목적**만 포함한다.

| 작성 기준 | 적용 규칙 |
| --- | --- |
| 단일 목적 | 기능 추가, 버그 수정, 리팩터링 등 서로 다른 목적 분리 |
| 독립 상태 | 각 커밋은 가능한 범위에서 빌드 및 테스트 가능한 상태 유지 |
| 구현과 테스트 | 동일 기능의 구현 코드와 관련 테스트는 하나의 커밋에 포함 가능 |
| 리팩터링 분리 | 기능 변경과 무관한 구조 개선은 별도 커밋으로 분리 |
| 사전 작업 분리 | 의존성 추가나 공통 설정처럼 후속 작업의 기반이 되는 변경 우선 커밋 |
| 작업 중 커밋 | 공유 브랜치에는 `WIP`, `수정`, `최종` 등 임시 커밋 미유지 |

아래 질문 중 하나라도 답이 다르면 커밋 분리를 우선한다.
- 변경 목적이 동일한가?
- 하나의 커밋 메시지로 모든 변경을 구체적으로 설명할 수 있는가?
- 해당 변경만 되돌려도 다른 변경이 손상되지 않는가?
- 기능 구현과 직접 관련된 테스트 또는 필수 설정인가?

```plain text
# 지양
feat(room): 공간 생성 기능 추가 및 코드 정리

# 권장
feat(room): 공간 생성 API 추가
refactor(room): 공간 생성 서비스 책임 분리
```
